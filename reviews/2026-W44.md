## M1 / M2 / W1 — due, not run (why)

14 full days of recorder data were reached on **2026-10-21 20:45 UTC**. I did not dispatch `m1` / `m2` / `w1`:

1. **Gap exclusion would leave almost nothing.** M1 §2 / M2 §2 / W1 §2 exclude coins whose life overlaps a
   recorder gap; the code drops a coin if *any* logged gap falls between its creation −60 s and +6,000 s. The recorder
   logs every websocket reconnect as a gap — in the status files I sampled: 15–950 reconnects per hour, typically
   200–900. A coin's 100-minute window almost always contains several. The few surviving coins would come from
   unusually clean runners, so the holdout would likely fail "≥ 300 PASS coins" → NO EVIDENCE for a data reason, and
   the one-time holdout would be spent. (Those gaps are real: trades during a reconnect are missing.)
2. **Size:** the loader downloads every recording (14.6 GB of tars) and loads all trades into memory at once. A
   GitHub runner has ~14 GB of free disk and 16 GB RAM, so the job would most likely crash before producing a result
   (a crash wouldn't spend the holdout, but it's 5 h wasted).

No outcome (dead rates, P&L, wallet results) was computed or looked at. Only data-quality fields (status files: gap
counts, row counts) were read, as allowed before a test.
